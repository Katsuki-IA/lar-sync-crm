## Authorization boundaries
- Route IA-stage and tag-definition mutations through authenticated server functions that verify the existing database-derived current role before invoking user-scoped RPCs; lead-tag associations and commercial CRM operations stay separate to preserve normal lead workflows.

## Settings presentation
- Reuse config-presentation primitives and scoped config-page/config-form/config-dialog styles for company, module and secretary settings; keep visual consistency separate from permissions and data operations.
## Secretary text interpretation (phase 1)
- Free-text secretary messages are orchestrated by src/lib/secretary-engine.ts, which only validates input and produces a sealed SecretaryCommand; all execution happens in one transactional RPC (private.hub_secretary_finalize via the service_role-only public wrapper) that locks the event, checks replay, revalidates sender/module/settings/offer, executes, records and enqueues the reply atomically. AI output is validated strictly in src/lib/secretary-interpreter.ts (enum listar/aceitar/recusar/desconhecido only), legacy ACEITAR/RECUSAR+code keeps precedence, and identity comes only from the server-validated channel/phone. OpenAI credentials/model stay server-only (src/lib/secretary-ai.server.ts). Free replies use the dedicated private.hub_secretary_replies outbox (never hub_secretary_notices/hub_whatsapp_outbox, whose constraints require an offer). DB objects live in docs/secretary-ai-fase1-candidato.sql (not applied) and are covered by real PGlite tests in src/lib/secretary-sql.test.ts.
